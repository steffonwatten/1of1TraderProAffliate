# Writing code

**This applies to every application on this engagement.** A project's own
`.claude/rules/` covers only what is specific to it.

**Why this exists:** on a prior engagement one project's admin screen reached
over five thousand lines — five times the next largest file, and three quarters
the size of that application's entire backend HTTP layer. **Nobody decided to
write a file that size.** It happened one reasonable addition at a time, because
the cursor was already there and nothing said stop.

That habit is the most expensive thing on a metered account. **An AI coding agent
is billed on the context it reads.** A one-line change inside a five-thousand-line
file costs the same to read as a rewrite. On that engagement the agent was the
majority of the bill.

---

## 1. New feature → new file. Every time.

**Before adding code, ask: does this belong in the file I already have open?**

Almost always the honest answer is no. The file is open because of the *last*
thing you did.

Every project's `CLAUDE.md` carries a **"where to put new code"** lookup — intent
→ directory. Use it. If the project does not have one, that is the first thing to
add.

**A page or screen file gets wiring only** — an import, a tab entry, a route line.
Four lines, not four hundred. If your change to it is longer than that, it
belongs in a new file.

## 2. 400 lines is the ceiling

The linter warns at 400 (`max-lines`). **A warning is not permission.**

If a file you are editing is already over, you do not have to fix it — but **do
not make it worse.** Put the addition in a new file and import it.

Where a project enforces this as an error, the existing offenders are
grandfathered into a **shrink-only** list. You may make a listed file smaller.
You may not make it bigger, and you may not add to the list.

## 3. Extract in layers, not all at once

When breaking up a large file, order matters:

1. **Shared helpers** — pure functions, no risk
2. **Shared presentational components** — no data fetching, no state
3. **Feature panels**, one at a time, verifying each

**Never move a component and change it in the same commit.** If something breaks
you need to know which of the two did it.

## 4. Delete before you share

Deduplicating something before removing its unused parts just moves unwanted code
into a shared package. One project had a component library where the application
used barely a quarter of it — the rest was deleted *first*, so the shared package
came out a quarter of the size it would otherwise have been.

When deleting, **compute the transitive closure, not direct usage.** A component
imported by another component rather than by the application looks unused and is
not; deleting on direct usage alone broke a build.

## 5. Two apps needing the same thing → a package, never a copy

One project carried dozens of byte-identical files across two frontends, because
some component libraries copy their source into your tree by design. Every fix
had to be made twice, or they drifted.

⚠️ **Tailwind 4 does not scan workspace packages.** Moving styled components into
one without an `@source` line leaves them compiling, building and rendering
**with no styling** — typecheck, lint and a full test suite all passed while the
entire interface was broken. **Verify by CSS bundle size.**

## 6. Generated code is never hand-edited

Where a project generates its API client and schemas from a spec, **the spec is
the source of truth.** Change it and regenerate.

Generated directories should be excluded from AI context and marked in
`.gitattributes`. If you find yourself reading them, stop.

## 7. Comments explain *why*

The diff already says what.

A comment restating the line below it is noise. A comment saying *"this looks
like a duplicate timer and isn't — don't delete one"* is worth its weight.
Several audit findings on a prior engagement were only reachable because a
comment explained intent, including one that identified a scheduler as dead code.

**Where a thing looks wrong but is right, say so and say why.** Those comments
are what stop a future session "fixing" something load-bearing.

## 8. Before you finish

- Typecheck — must be **0**
- Lint — must be **0 errors** (warnings are fine)
- Touched the frontend? **Build it.** Typecheck, lint and a full test suite once
  all passed on a change that left the entire interface unstyled. The build
  caught it; nothing else could.
- Check the test **count**, not just the exit code. Tests can fail at *import*
  and report "no tests" rather than a failure — green-ish output nobody
  investigates.

Then follow `finishing-work.md` — commit, push, open the PR, session log, and
walk the client through the deploy one step at a time.

---

## The test for all of this

**Could someone find this code without reading a file they didn't need to?**

If the answer is no, it is in the wrong place — regardless of whether it works.
