# Git remotes

**The GitHub remote is named `origin`. Always. On every project, on every
machine, and inside the hosting platform's workspace.**

Not `gh`. Not `github`. Not `upstream`. `origin`.

This is not a style preference. **The hosting platform's git pane only recognises
a remote called `origin`** — so does the pull/push machinery behind it. Give the
remote any other name and the pane shows **no pull button at all**, pulls fail,
and nothing explains why. The repo looks connected. It *is* connected. It just
cannot be used from the UI.

That is the failure mode: not an error, an **absence**. There is nothing to read,
so the natural response is to reconnect the repository again — which does not
help, because reconnecting does not rename anything.

---

## Why this rule exists

On a prior engagement a remote was set to `gh`, because a rules file **told a
session to do exactly that**:

```bash
git remote set-url gh https://github.com/<owner>/<repo>.git   # ❌ wrong
```

Consequences, all downstream of that one word:

- The git pane never showed a pull button, on any of the several occasions the
  repo was reconnected.
- `main` had **no upstream**, so `git pull` needed the full `git pull gh main`
  form — which is why the docs of that era are full of that phrasing.
- Because pulling was awkward, it was skipped. The platform workspace and GitHub
  drifted several commits apart in both directions.
- Untangling it meant asking the **billed** agent — for a problem created by a
  rules file.

The rule that caused it has been corrected. **It is left visible in the file it
was wrong in**, per the rule on keeping corrections visible: a session that finds
the old command elsewhere needs to know it was wrong, not wonder which of two
instructions to follow.

## Setting it up correctly

```bash
git remote -v                                    # what is it actually called?
git remote rename gh origin                      # if it is anything but origin
git branch --set-upstream-to=origin/main main    # so plain `git pull` works
```

After that, `git pull` and `git push` work bare — in a shell, and as buttons in
the platform's git pane.

**Verify both, not just the first:**

```bash
git remote -v                                         # → origin
git rev-parse --abbrev-ref --symbolic-full-name @{u}  # → origin/main
```

A correctly-named remote with no upstream still leaves the pane half-broken.

---

## Never put a token in the remote URL

```bash
git remote set-url origin https://<token>@github.com/...   # ❌ never
```

`git remote set-url` writes the URL **verbatim into `.git/config` in plain
text**. A token there is a committed-adjacent credential sitting in the working
tree. See `secrets.md`.

It has also failed in the dumbest possible way: a placeholder was pasted in
literally — `https://PASTE_TOKEN_HERE@github.com/...` — leaving a remote that
failed confusingly for a long time afterwards.

**On your own machine, use SSH** (`git@github.com:...`). **Inside the platform,
use its git pane**, which holds its own credential.

---

## When the platform says it cannot authenticate

> *"Invalid username or token. Password authentication is not supported."*

That means the workspace's stored GitHub credential **expired**. Nothing is
misconfigured, and it is **not** the remote name.

**Use the git pane** — its refresh and pull authenticate separately from shell
git and work fine. Do **not** mint a personal access token for this. It is
slower, and it puts a live credential on the clipboard and from there usually
into `.git/config` or a chat message.

---

## When the two sides have drifted

Divergence is normal — you push to GitHub, the client commits inside the
platform, and the platform's agent commits on its own whenever it checkpoints. It
is only a problem when it is left.

```bash
git fetch origin
git log --oneline --left-right --graph origin/main...HEAD
```

`<` is on GitHub only, `>` is local only. If both sides have commits, **merge and
push — do not work around it.** A pull that is postponed because it is fiddly is
how a repo ends up several commits apart in both directions.

**Check this before starting work in the platform's workspace**, not after
building something on top of a stale tree.

---

## The one-line version

> If a git pane has no pull button, the remote is not called `origin`.

Check that before reconnecting the repository, before minting a token, and before
asking a billed agent.
