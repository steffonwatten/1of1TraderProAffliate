# Querying the live database

**In a cloud session, `psql` will hang. Don't try it. Use HTTP.**

Three separate sessions on a prior engagement each spent several minutes
rediscovering this from scratch, so it is written down rather than re-derived.

---

## Why

Cloud sessions reach the network through an **HTTP proxy**. The standard Postgres
port is not forwarded, so a raw socket never connects — and it does not fail
cleanly, it **hangs** until something times out. A timeout rather than a refusal
is the signature.

**Adding the host to the environment's allowed domains does not change this.**
The allowlist governs HTTP/HTTPS; it cannot open a TCP port. Several attempts
were wasted on the allowlist before that was worked out.

Most managed Postgres providers also expose **SQL over HTTPS on 443**, which does
traverse the proxy. That is the route to use.

---

## How

The credential is the database URL in the environment. It is a `SELECT`-only
role — it cannot write, update, drop or grant. See `secrets.md` for why it is
deliberately there.

Install the provider's HTTP driver **in scratch space, not in the repo**:

```bash
cd /tmp && npm install <provider-serverless-driver>
```

Then query through it, reading the URL from the environment.

**Do not add that driver to `package.json`.** The application does not use it —
it connects over TCP, which is correct everywhere the app actually runs.

Confirm which database you are on **before drawing any conclusion**:

```bash
node -e "console.log(new URL(process.env.DATABASE_URL).host)"
```

---

## ⚠️ The platform's shell is NOT production. It is a different database.

**The database URL inside the hosting platform's shell frequently points at the
platform's own managed Postgres, not at the production database.** They are two
separate databases with the same schema, so every query and every write *appears*
to succeed — against the wrong data.

**This has already caused a silent production incident.** On a prior engagement a
backfill was run from the platform shell to recover a message outage. It reported
`inserted: 84` and looked perfect. **None of it reached production.** The 84
messages — and the opt-out requests they contained — went into the development
database, so customers who had asked to stop being contacted were still unblocked
in the live system.

The counter was not lying. The code only counts a row after the database confirms
the write. **It wrote to the other database.**

So, for anything that touches real data:

| Need | Run it |
|---|---|
| A script that **writes** (backfill, recompute, seed) | Through the **deployed app** — an authenticated admin HTTP endpoint. It holds production's real credential |
| A **read or export** of production | A machine with the read-only production URL, or a cloud session over HTTPS as above |
| Anything at all | **Never assume a script run in the platform's shell hit production** |

Write backfill and maintenance logic in shared library code so it can back
**both** a script and an admin route — then prefer the route. Calling it as the
logged-in admin from the browser console on the live site works, because the
session cookie authenticates it:

```js
await fetch('/api/admin/<task>?dryRun=1', { method: 'POST' })
  .then(r => r.json()).then(r => console.log(JSON.stringify(r, null, 2)))
```

**Verify writes against production afterwards. Never trust the summary line.**

---

## Where this does NOT apply

- **On your own machine, and inside the hosting platform**: the Postgres port
  works normally. Use `psql`.
- **The application itself** always uses TCP. Do not change that to make a cloud
  session more convenient — every query in the app goes through it, and HTTP
  drivers do not handle transactions or pooling the same way.

So: **the app cannot run against the database in a cloud session.** The AI can
answer questions about live data; the application cannot serve it. If you need
the running app against real data, that is a job for a server or the platform.

## Two traps that have already cost time

### 1. Check the actual column types before casting

A `CLAUDE.md` note that *"money is numeric and the ORM returns it as a string"*
is about the **JavaScript** side. In SQL those columns are usually plain
`numeric`.

Two separate sessions read that line, assumed text, wrapped the columns in
`NULLIF(x,'')::numeric`, and both failed with:

```
ERROR:  invalid input syntax for type numeric: ""
```

`COALESCE(x, 0)` was all that was ever needed. **Read the schema, don't infer it
from a comment about a different layer.**

### 2. Bulk personal-data exports are blocked, and that is correct

The HTTPS route works fine for **counts and aggregates** — it has returned live
deposit counts and lead counts without trouble. A request that pulls **names,
emails and phone numbers in bulk** is stopped by a safety classifier, in a cloud
session and on a server alike.

**Do not look for a way around it.** That boundary is doing its job: a prior
engagement has already needed a git-history rewrite over tens of thousands of
customer records that reached a repository.

An export of customer records is a **deliberate human action**, run outside any
cloud session, writing to the archives directory — **outside any repo**.

**Never write a customer-data CSV into a repo working directory.** One `git add
-A` and it is on GitHub permanently.
