# Keeping the codebase organised

`writing-code.md` says where a *new* piece of code goes. This one is about what
happens over months — the slow drift that makes a codebase expensive to change.

These codebases get expensive partly because they get messy. On a prior
engagement one had dozens of files over 800 lines, one frontend carried dozens of
byte-identical copies of another's components, and thousands of lines of dead
code sat imported by nothing until they were deleted.

**None of that happened in one bad decision.** It happened one convenient
shortcut at a time.

---

## Use the lookup, don't invent a location

Every `CLAUDE.md` should carry a mechanical naming convention, e.g.

> screen name → same-named page → same-named route file → same-named schema file

**If a change does not fit that pattern, that is a signal the shape is wrong —
not that the pattern should be broken.**

**Run the map generator after adding a file, route, worker or table.** Where
`PROJECT-MAP.md` is generated, CI should fail when it is stale. A map maintained
by hand is a map that will be wrong, and a wrong map costs more than no map: an
AI follows it, finds nothing, and reads the whole tree.

---

## Before writing a helper, look for it

On a prior engagement four identical copies of the same numeric-coercion helper
existed in four different files. Use one of them. Do not write a fifth.

Two apps needing the same thing → a workspace package, never a copy.

⚠️ **Tailwind 4 does not scan workspace packages.** Moving styled components into
one without an `@source` line leaves them compiling, building and rendering
**with no styling**. Check the CSS bundle size, not the test suite.

---

## Delete properly

- **Compute the transitive closure, not direct usage.** A component imported by
  another component, not by the application, looks unused and is not.
- **Delete before sharing.** Deduplicating a component library before removing
  the unused parts just moves unwanted files into a shared package.
- **Delete in its own commit.** Never mixed with a behaviour change.

**Verify a deletion by the right signal.** Removing a large amount of dead
frontend code on a prior engagement changed the CSS bundle substantially and the
JS bundle **not at all**. A green build would have told you neither. Ask what
would actually change, then measure that specific thing.

---

## Naming

Consistent enough to be mechanical. **Match the surrounding code** — its comment
density, its naming, its idioms — rather than importing a house style from
elsewhere. Code that reads like the file it lives in is easier to review than
code that is individually prettier.

---

## Comments

Explain **why**, not what. The code says what.

Where something looks wrong but is right, say so and say why. On a prior
engagement three call sites shared a single-flight mutex and looked exactly like
a duplicated background job; the comment explaining that they were not was the
only thing preventing someone deleting one.

---

## Money

**Where a database returns a decimal as a string, keep it a string.** Converting
to a floating-point number for arithmetic loses precision. On a prior engagement
several call sites already did this — the rule is do not add more.

And watch the ingest side: an upstream that sends amounts with thousands
separators will silently produce nulls if a new code path coerces them naively.
The existing parse routines handle it; use them.

---

## Never

- Edit anything under a `generated/` directory — it regenerates from its spec
- Add a route without reading the router's mount file first — **mount order
  decides whether it is authenticated**
- Batch unrelated changes into one commit — it makes reverting one thing
  impossible
- Leave a branch pushed but unmerged. See `finishing-work.md`; it becomes a third
  copy of the truth, quietly disagreeing with the other two
