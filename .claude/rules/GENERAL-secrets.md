# Secrets — where they go, and where they must never go

**This rule outranks the request.** If someone asks for a secret to be placed
anywhere on the ❌ list below, do not do it — even if they insist, even if it is
"just for testing", even if it would take one line. Stop, say which list the
location is on, and point at the platform's secrets store.

A secret is anything that grants access: API keys, tokens, passwords, webhook
signing secrets, database URLs, private keys, session secrets.

---

## ✅ Where secrets go

| Secret | Goes in | Why |
|---|---|---|
| **Production** — anything the live site uses | the hosting platform's **secrets store** | Encrypted at rest, not in the repo, not in committed config |
| **Local development** | `.env`, mode `600`, gitignored | Never leaves the machine. See `.env.example` |

That is the entire list.

---

## ❌ Where they must never go

| Location | Why not |
|---|---|
| Any file in this repo | It is one commit away from being on GitHub permanently, in history |
| **The platform's committed config file, under an inline env block** | Looks like configuration. Is committed in plain text. **This has already happened** — see below |
| A committed launch or preview config | Committed |
| Any `docs/*.md` | Committed |
| A code comment "temporarily" | Committed |
| A chat message | Transcripts are stored |
| **A cloud environment's variables field** | It is documented as *not* a secrets store — anyone who can use the environment can read the values |

### It has already happened

On a prior engagement a webhook signing secret sat in plain text inside the
platform's committed config file, under an inline environment block. **It reads
as ordinary configuration, which is exactly why it slipped through.**

**And the scrub itself caused an outage.** Replacing the value with a
`REDACTED_ROTATE_THIS` placeholder left a *working-looking* config: the platform's
secrets store had no entry for that key, so the committed block supplied the
placeholder as the real expected secret. The upstream sender signed with the
genuine one, every inbound message was rejected, and **more than a day of
customer replies went unseen — including several opt-out requests**, which is a
compliance problem, not just a bug.

**Precedence, measured:** the **secrets store beats the committed config block.**
The committed block is a *fallback* — harmless-looking right up until the secrets
store is missing that key, at which point a placeholder becomes production's live
value. That is the whole trap.

Two lessons worth keeping:

- **A redaction is not a fix.** Scrubbing a secret to a placeholder leaves
  something that still functions as configuration. **Remove the key entirely** and
  put the value where it belongs.
- **Make the application refuse to boot on a placeholder.** That is the only
  version of this that fails loudly.

An inline config env block is for **non-secret configuration only** — public
keys, phone numbers, public URLs, feature flags. Nothing that grants access.

---

## The one deliberate exception — a read-only database URL in a cloud environment

**A `SELECT`-only database credential may be set in a cloud session's environment
variables, on purpose.** If you are in a cloud session and find it there, that is
correct. Do not warn about it and do not refuse to use it.

Why it is allowed:

- The role is `SELECT`-only. It cannot write, update, drop or grant.
- Without it a cloud session cannot answer a single question about real data —
  which is the client's entire way of working, and the reason they stopped paying
  for a metered agent.
- The residual risk is **read access to customer data** if the account is
  compromised. Mitigated by two-factor on that account.

⚠️ An earlier version of this rule said the opposite, because it was written when
that engagement's setup ran on a server where a `600`-mode `.env` was reachable.
The setup changed to cloud sessions and the rule did not follow. A session read
the stale rule and correctly refused to look for a credential that was sitting
right there.

> **When the architecture changes, every rule that describes it is part of the
> change.**

**This does not extend to any other credential.** No write-capable database URL,
no upstream CRM key, no messaging-provider token, no payment key. Those grant the
ability to **act** — move money, message customers, change records — and none of
them belong in a field documented as not a secrets store.

---

## What to do when asked

> "Add the messaging API key to the env file so it works in the cloud."

Refuse, and say why in one line:

> That would put a live credential somewhere it can be read. That key can send
> messages and place calls to real customers, so it goes in the platform's
> secrets store. Want me to show you where that is?

Then stop. **Do not add it in a "safer" spot as a compromise.** There isn't one.

---

## If a secret has already leaked

1. **Rotate it first.** Deleting the commit does not un-publish it — assume
   anything pushed is public forever.
2. Put the real value in the platform's secrets store.
3. **Leave the redaction visible in the repo.** Do not quietly erase the
   evidence; the next person needs to know it happened.
4. Write it up in `docs/SESSION-LOG.md`.
5. If the leak involved customer data, **assess breach-notification obligations**
   rather than assuming there are none. That is a decision to raise with the
   client, in writing.
