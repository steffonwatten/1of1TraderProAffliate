# Finishing a piece of work

**The client will not ask you to commit.** They are not a developer, and on the
platform there was nothing to ask for — the agent checkpointed by itself. If you
wait to be told, work sits uncommitted until something is lost.

So: **finish the job without being asked.** Every one of these, every time.

---

## The loop

### 1. Verify it, by the right signal

Not "typecheck passed". Ask what would actually break if this were wrong, then
check **that specific thing**.

On a prior engagement a change passed typecheck, lint **and a full test suite**
while leaving the entire interface unstyled. On the same account three tests were
verifying nothing — two stale mocks, and one that deliberately disabled the
security check it existed to cover.

Check the test **count**, not just the exit code: tests can fail at *import* and
report "no tests" rather than a failure.

**If you cannot verify it, say so plainly** rather than implying it works.

### 2. Commit it

One change, one commit. Explain **why**, not what — the diff already says what.

### 3. Push it, and open the PR

`git push`. Unpushed work exists on one machine and is invisible to CI.

**Then open a pull request and get it merged.** A branch that is pushed but never
merged is not finished — it is a third copy of the truth, quietly disagreeing
with the other two.

That is not hypothetical. On a prior engagement a cloud session built a feature,
pushed the branch, and stopped. Nobody opened a PR. The platform workspace merged
it locally instead, so `main`, the branch and the workspace all diverged — and
days later a routine `git pull` failed with conflicts in three files. **Untangling
it took longer than the feature did.**

```bash
gh pr create --fill
gh pr checks --watch
gh pr merge --squash --delete-branch
```

If CI is red, fix it. **A branch left open because the tests fail is the same
problem with extra steps.**

### 4. Add a `docs/SESSION-LOG.md` entry

Newest first. What changed, why, and **how it was verified**. Record what you
investigated and chose *not* to do, and why — that half has already stopped a fix
landing that would have broken outbound customer messaging.

### 5. Walk them through the deploy — one step at a time

**Pushing does not make it live, and they will not infer that.**

**Do not hand them all the steps at once.** Give one, wait for them to come back,
then give the next. That way a failure is caught at the step it happened on
instead of three steps later.

Say this, roughly:

> That's pushed. Now go to the platform, open the **Shell** tab — not the agent
> chat — and paste this:
>
> ```
> git pull
> ```
>
> Let me know if you get stuck, or tell me when it's done.

**Wait. Do not continue until they answer.**

If it worked:

> Now hit **Preview** and have a look. Tell me if it looks right.

Wait again. If they say it looks good:

> Go ahead and **Publish**. That's what makes it live for customers.

**If they say something looks wrong — stop.** Do not tell them to publish. Find
out what they are seeing first.

**Why the shell and not the agent chat:** every agent message is billed. The
shell is free and does the same job. If they ask the agent to pull for them, that
is a charge for something that costs nothing. Say so if it comes up — it is the
entire point of the engagement.

**Never tell them to publish something you have not verified**, and never tell
them it is live. Only they can see the live site. Ask them to confirm.

## 🔴 Added a database table? It will NOT exist in production.

**Platforms that generate migrations usually only generate them for changes their
own agent makes.** Anything arriving through `git pull` is ignored, so a new table
silently does not exist — and the first symptom is a page that looks *empty*
rather than broken.

That happened on a prior engagement: the schema was on `main`, the code was
deployed, and three sections of a page showed "nothing here" for an hour because
every query touching that table was throwing a 500.

### And it is worse than "the migration is missing"

**Measured on a prior engagement.** The tables were created in **production
only**. The next publish then offered this, one click from being approved:

```sql
DROP TABLE "..." CASCADE;
DROP TABLE "..." CASCADE;
DROP TABLE "..." CASCADE;
```

**The publish step makes production match DEVELOPMENT.** It diffs the two
databases, and anything production has that development does not is treated as
drift to be removed. Creating a table in production alone therefore *guarantees*
a destructive migration on the next publish.

So, when a change adds a table, say so explicitly and give the SQL:

> This adds a table. It will not exist in production after publishing.
> Run this in **BOTH** the Development and the Production database — in the
> **Database pane**, using the database selector at the top:
>
> ```sql
> CREATE TABLE IF NOT EXISTS ... ;
> ```

1. Run it in the **Development** database.
2. Run the same block in the **Production** database.
3. Then publish. The migration step should list nothing destructive.

Use `CREATE TABLE IF NOT EXISTS` so running it twice is harmless.

⚠️ **Not the shell, and not a schema-push command.** The shell's database URL
often points at the platform's own Postgres, not production — the table would be
created in the wrong place and the page would still be empty. See
`querying-live-data.md`.

🔴 **Always expand the migration list before approving a publish.** It usually
sits behind a warning icon and a collapsed chevron, and it is the **last point at
which a `DROP TABLE` can be stopped.** If it proposes dropping anything you
recognise, cancel, fix the dev/prod mismatch, and re-run the publish.

## 🔴 "The page is spinning" — the three causes, in the order to check them

**A spinning preview is almost never a slow query.** The page renders its shell,
its first API call never resolves, and it hangs. Check in this order — cheapest
first, and each has been the answer at least once.

### 1. Is anything actually running?

Ask this **first, every time.**

On a prior engagement a spinning preview was diagnosed for over an hour: two
databases, six tables, auth credentials, port mappings. The cause was that the
API server had been terminated during a merge. `ss -tlnp | grep :PORT` had
already printed **nothing listening**, and the investigation carried on into
tables anyway. The platform's own agent identified it in one sentence, for about
a dollar.

The symptom misleads: the page renders its shell and then hangs, which looks like
slow data rather than a dead server.

**And when the platform owns the process, restart it the platform's way.**
Starting it by hand in a shell produces a server that dies with the window, which
is worse than not fixing it — the client reasonably asks why they now have to
keep a terminal open, and the answer is that they shouldn't.

### 2. Is every request coming back `401`? → a dev auth flag is missing

Where authentication has been hardened to **fail closed**, e.g.

```ts
export const DEV_BYPASS_ENABLED =
  process.env.AUTH_DEV_BYPASS === "1" && NODE_ENV === "development";
```

…both conditions are required, neither inferred. That hardening is right: it
replaced copies of a `NODE_ENV !== "production"` gate that **failed open** — an
unset or misspelled `NODE_ENV` turned every request into a master admin on a
system holding customer financial records.

**What it breaks:** if nothing sets the new flag in the workspace dev
environment, the frontend's own bypass still lets the UI load happily while every
API call 401s, and the page spins forever. **The symptom looks like slow data. It
is a locked door.**

Set the flag in the platform's **development-scoped** env block, never the shared
one. Shared applies to the deployment too — the flag is still harmless there if
production sets `NODE_ENV=production`, but relying on one lock when two were
designed in is how the first fail-open gate got written.

⚠️ **If that config block is ever lost, the preview breaks again and looks
exactly like a data problem.** Check it before debugging a single query.

**❌ What this rule used to say, and why it was wrong.** It claimed the spinner
was because *"the preview URL is a fresh temporary address each session, so no
auth session carries over."* That reads plausibly, matches the 401s, and is **not
the cause.** A session read it, went looking at auth credentials and port
mappings, and lost an hour.

> Left visible on purpose: **a confident wrong explanation costs more than no
> explanation, because it stops the search.**

### 3. Does the feature need a table that only exists in production?

Preview runs against the **development** database. A table created in production
only will 500 there while being fine live. Symptom is an empty section or a
spinner, not an error page.

---

**So before sending them round the preview loop:** open the console and read the
status codes.

- `401` everywhere → cause 2
- Nothing logged at all → cause 1
- A `500` on one route → cause 3

If none of it can be fixed quickly, **say plainly that preview cannot show it**,
state what *has* been verified (CI, tests, build) and what has not, and verify on
the live site immediately after publishing.

## Git remotes → `git-remotes.md`

**The remote is named `origin`.** That file covers remote naming, upstreams,
expired platform credentials, tokens in URLs, and what to do when the platform
workspace and GitHub drift.

**❌ An earlier version of this file ended with this command, and it was wrong:**

```bash
git remote set-url gh https://github.com/<owner>/<repo>.git   # ❌
```

Naming the remote `gh` means **the platform's git pane shows no pull button at
all** — it only recognises `origin`. The pane looks connected and simply cannot
pull, with nothing on screen to explain it. On a prior engagement that led to the
repo being reconnected several times, `main` having no upstream, pulls being
skipped because they were awkward, and the two sides drifting several commits
apart before a billed agent call untangled it.

Left visible rather than deleted, because the wrong command was followed once and
may still be quoted somewhere. **Where `git pull <remote> main` appears in older
docs, it is a leftover of the same mistake. `git pull` on its own is correct.**

## Do not

- **Do not commit secrets, customer data, or anything in `.gitignore`.** See
  `secrets.md`. Check `git status` before staging; never `git add -A` blindly.
- **Do not push straight to `main` if the change is risky.** Branch, and say why.
- **Do not report success you have not verified.** If tests fail, say they fail
  and show the output. A confident wrong answer costs more than an honest
  "I couldn't check this."
- **Do not batch unrelated changes into one commit.** It makes reverting one
  thing impossible.
- **Do not act on anything outside the repo without asking.** On a prior
  engagement files were deleted after reading a client's frustration as a
  decision to decline, and a system service was enabled from a stale document
  that logged the client out of their own tooling. Both recoverable, both
  avoidable by asking first.

## When they ask for the same thing twice

Say so:

> You've asked for this twice now. Want it as a screen instead? Then it's a
> button instead of a request every time.

This is not a nicety — **it is the mechanism behind the bill.** Operations the
application could not perform were performed repeatedly, by hand, by an AI, at a
metered rate. Turning a repeated question into a permanent feature is the single
most valuable thing you can do here.
